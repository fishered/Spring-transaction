What guides the design

先把故障讲清楚，
再写事务框架。

跨服务调用总会遇到重试、超时和节点切换。组件要让这些状态有记录、有判断依据，也有下一步动作。

01 / 记录

每一步都可追踪

协调器持久化流程与步骤状态。进程退出后，新的工作节点能从数据库继续执行。

02 / 判断

超时先查结果

响应丢失不等于执行失败。用稳定的操作 ID 查询参与方，再决定推进或补偿。

03 / 恢复

重复调用仍安全

参与方把业务变更与幂等记录放在同一个本地事务中，并拒绝迟到的执行请求。

Architecture

嵌入式协调，
各服务自主管理数据。

发起服务引入 Starter，多个实例共享协调器状态库；每个参与服务保留自己的数据库和业务事务。

  • 显式定义执行、查询与补偿接口。
  • 协调器使用数据库租约和版本检查切换工作节点。
  • 跨服务传输可替换，核心逻辑不绑定 HTTP 或消息队列。

Guarantees & limits

明确保证范围。

当前实现提供可恢复的最终一致性。业务必须为补偿和不可逆副作用作出明确设计。

已实现

  • 稳定业务键与操作 ID，支持请求去重。
  • 持久化执行进度，节点故障后继续处理。
  • 区分成功、补偿完成和需要人工处理。
  • 超时后查询结果，明确失败后逆序补偿。

能力边界

  • 跨 HTTP 服务不具备即时原子提交。
  • 补偿逻辑由业务编写，并需保证幂等。
  • 外部支付或通知需要自身的幂等与撤销能力。
  • PostgreSQL/MySQL 兼容性与生产压测尚待验证。
